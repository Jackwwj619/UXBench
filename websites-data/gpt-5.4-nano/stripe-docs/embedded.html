Stripe Checkout / Embedded page
Current API flow

Embed Stripe Checkout on your site without freezing the docs in an old API version.

This rebuild follows Stripe’s current embedded quickstart: create a Session with ui_mode: 'embedded_page', return the client_secret, mount with stripe.createEmbeddedCheckoutPage(), and use return_url to resume after redirect-based methods.

  • Replaces stale ui_mode: 'embedded' examples with the current embedded page flow.
  • Shows the exact difference between embedded Checkout and a fully custom Elements integration.
  • Keeps all the utility features from the hosted flow, including working copy and search behavior.
Why embed

Keep checkout on your domain while Stripe still owns the secure payment UI

Customers stay on your page, but Stripe handles the iframe, the payment confirmation states, and the return path for redirect-based methods.

embedded_page Current Checkout Session ui_mode
client_secret Returned by the server and consumed by Stripe.js
return_url Needed for redirect-based payment methods and retries
Decision point
0

When to use the embedded page instead of hosted or Elements

Embedded Checkout is the middle ground. You keep the payment form in-page, but you still let Stripe manage the form lifecycle and most payment-method complexity.

Embedded page

Best when you want in-page checkout with low code

Use the Checkout Sessions API plus Stripe.js. Your server returns a client_secret, and the client mounts the page with stripe.createEmbeddedCheckoutPage().

  • Customers stay on your site for the main payment step.
  • Branding is still limited compared with fully custom Elements.
  • Stripe handles redirect-based payment methods through the return_url.
Elements

Use only when you need deeper UI control

Elements gives you the most control, but it also asks you to manage more UI state, layout, and integration details. Stripe positions Checkout Sessions plus Elements as a more advanced build.

  • Custom layout and component composition.
  • More code and more surface area to maintain.
  • Recommended only if Checkout’s limited customization isn’t enough.

Do not nest Checkout inside another iframe

Stripe explicitly warns against placing embedded Checkout inside your own iframe because some payment methods need to redirect the customer to another page to complete confirmation.

2

Create an embedded Checkout Session on the server

Create the Session server-side, set ui_mode: 'embedded_page', and return the Session’s client_secret to the client. For this flow, success_url is not allowed. Instead, use return_url.

Why return_url still matters

Even though the payment form is embedded, some payment methods still redirect the customer to an intermediate bank or wallet page. Stripe sends them back to your return_url and substitutes {CHECKOUT_SESSION_ID} so you can recover the Session state.

server.js 
const express = require("express");
const Stripe = require("stripe");

const app = express();
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);

app.post("/create-checkout-session", async (req, res) => {
  const session = await stripe.checkout.sessions.create({
    line_items: [
      {
        price: "price_12345",
        quantity: 1,
      },
    ],
    mode: "payment",
    ui_mode: "embedded_page",
    return_url: "http://localhost:4242/return?session_id={CHECKOUT_SESSION_ID}",
  });

  res.json({ clientSecret: session.client_secret });
});
server.py 
import os

Embedded page rules that differ from hosted Checkout
ui_mode
Use embedded_page for the full embedded page flow. This is the current setting in Stripe’s embedded quickstart and API reference.
client_secret
Return it to the frontend so Stripe.js can mount the embedded Checkout UI.
return_url
Required when redirect-based payment methods are enabled. Stripe appends the Checkout Session ID when it sends the customer back.
success_url
Not allowed in the embedded page flow. Use return_url and then inspect the Session status on your return page.
3

Mount the embedded page with Stripe.js

Stripe.js loads the embedded Checkout page into an empty container. The client doesn’t build the payment form itself; it only provides a function that fetches the Session secret from your server.

checkout.html 
<div id="checkout"></div>

<script src="https://js.stripe.com/v3/"></script>
<script>
  const stripe = Stripe("pk_test_12345");
  initialize();

  async function initialize() {
    const fetchClientSecret = async () => {
      const response = await fetch("/create-checkout-session", {
        method: "POST",
      });

      const { clientSecret } = await response.json();
      return clientSecret;
    };

    const checkout = await stripe.createEmbeddedCheckoutPage({
      fetchClientSecret,
    });

    checkout.mount("#checkout");
  }
</script>

4

Build a return page that can resume or finish the flow

When Stripe returns the customer to your site, fetch the Session using the ID from the URL and branch on its state. Stripe’s guidance is simple: complete means show success; open means let the customer try again.

server.js 
app.get("/session-status", async (req, res) => {
  const session = await stripe.checkout.sessions.retrieve(req.query.session_id);

  res.json({
    status: session.status,
    paymentStatus: session.payment_status,
    customerEmail: session.customer_details?.email,
  });
});
server.py 
@app.get("/session-status")
def session_status():
    session = stripe.checkout.Session.retrieve(request.args.get("session_id"))
    return jsonify({
        "status": session.status,
        "paymentStatus": session.payment_status,
        "customerEmail": session.customer_details.email if session.customer_details else None,
    })
server.rb 
get "/session-status" do
  session = Stripe::Checkout::Session.retrieve(params[:session_id])

  {
    status: session.status,
    paymentStatus: session.payment_status,
    customerEmail: session.customer_details&.email,
  }.to_json
end
server.php 
$session = \Stripe\Checkout\Session::retrieve($_GET["session_id"]);

echo json_encode([
    "status" => $session->status,
    "paymentStatus" => $session->payment_status,
    "customerEmail" => $session->customer_details?->email,
]);
return-page.js 
const params = new URLSearchParams(window.location.search);
const sessionId = params.get("session_id");

const session = await fetch(`/session-status?session_id=${sessionId}`).then((res) => res.json());

if (session.status === "open") {
  // Remount embedded Checkout so the customer can try again.
} else if (session.status === "complete") {
  // Render a success state and show order details.
}
Status

complete

The payment succeeded. Render a success state and pull any customer-facing details you want from the Session response.

Status

open

The payment failed, was canceled, or needs the customer to retry. Remount embedded Checkout instead of acting like the order is done.

5

Use webhooks for fulfillment, not just the return page

The return page is important for UX, but not reliable enough for order fulfillment. Stripe says the same thing here as in the hosted flow: your backend should act on webhook events.

Event What it means Typical action
checkout.session.completed The customer completed the Checkout Session successfully. Send order confirmation and fulfill the purchase.
checkout.session.async_payment_succeeded A delayed payment method eventually succeeded after Checkout completed. Fulfill once the asynchronous confirmation arrives.
checkout.session.async_payment_failed A delayed payment method later failed. Notify the customer and guide them back on-session to retry.
Same reliability rule as hosted Checkout

Customers can close the tab before your return page loads. If fulfillment depends on that page rendering, you will miss successful orders.

6

Test success, authentication, decline, and redirect behavior

Stripe’s embedded guide tests the same core card paths as the hosted flow, but the embedded page is also where redirect behavior becomes especially important.

Scenario Test method Expected behavior
Success 4242 4242 4242 4242 Payment succeeds immediately.
3DS challenge 4000 0025 0000 3155 Customer completes authentication before the Session finishes.
Decline 4000 0000 0000 9995 The payment is declined and the Session stays recoverable.
Redirect method Alipay, Bancontact, EPS, iDEAL, or similar Stripe leaves the page temporarily, then sends the customer back through return_url.
