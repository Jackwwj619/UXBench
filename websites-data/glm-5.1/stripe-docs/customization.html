Stripe Checkout / Customization
Reality-checked

Customize Checkout without inventing controls Stripe doesn’t actually offer.

This page removes the fake “everything is configurable” framing and replaces it with the real Stripe Checkout surface: branding settings, branding_settings, text and policies, blocked card brands, custom domains for hosted pages, and product images from Products or inline product_data.

  • Hosted Checkout and embedded page do not expose the same branding surface.
  • Custom domains apply to Stripe-hosted pages, not to the embedded page on your own site.
  • Policy text is flexible, but Stripe explicitly warns against creating ambiguous or non-compliant copy.
Customization limit

Checkout stays opinionated on purpose

Stripe Checkout is meant to stay low-code and high-conversion. You can brand it, annotate it, and restrict certain payment details, but you cannot turn it into a fully bespoke checkout UI.

What Stripe Checkout actually lets you change

Stripe Checkout offers limited customization. That is part of the product design. The safe mental model is: you can brand the shell, add policy and support details, tune some payment restrictions, and enrich the product context. If you need total layout control, Checkout probably isn’t the right tool.

Hosted page

Most complete branding surface

The Stripe-hosted page can use your own logo or icon, custom colors, supported fonts, border style, business name, product images, legal policies, support details, and even a custom subdomain.

  • Supports logo and icon in branding settings.
  • Supports custom domains because Stripe hosts the checkout URL.
  • Still limited to Stripe’s overall page structure.
Embedded page

Same policy tools, narrower visual surface

The embedded page inherits the same general Checkout behavior but narrows some presentation controls. Stripe documents background color, button color, font, shapes, and display name, not a full logo-and-icon treatment inside the iframe.

  • Uses the same branding_settings object with embedded-page-specific limits.
  • Does not need a custom domain because it already renders on your site.
  • Shares card-brand filtering, policies, and product-image behavior with hosted Checkout.

Appearance and branding settings

Stripe documents two ways to brand Checkout: Dashboard settings and per-session branding_settings. If you omit a field in branding_settings, Checkout falls back to the Dashboard default.

Hosted and embedded do not expose identical visual controls

Stripe’s appearance docs show logo and icon controls on the hosted page, while the embedded page documentation centers on display name, background color, button color, font family, and border shape.

Branding controls Stripe documents
branding_settings.display_name
Overrides the business name shown in Checkout. Stripe also lets you set the default in Business details.
branding_settings.background_color and button_color
Control the main surface and primary action color. If you skip them, Stripe uses your Dashboard defaults.
branding_settings.font_family and border_style
Choose from Stripe’s supported font list and supported shape presets. Locale fallback still applies if a font doesn’t cover the active character set.
branding_settings.logo and icon
Available on the hosted page flow. The hosted appearance docs explicitly show both options and how Checkout uses the icon as the favicon when present.
Node.js 
const session = await stripe.checkout.sessions.create({
  line_items: [
    {
      price: "price_12345",
      quantity: 1,
    },
  ],
  mode: "payment",
  success_url: "https://example.com/success",
  branding_settings: {
    display_name: "Powdur",
    font_family: "roboto",
    border_style: "rectangular",
    background_color: "#7D8CC4",
    button_color: "#A0D2DB",
  },
});

Text, policies, support details, and terms

Stripe Checkout supports more than colors. You can add operational text, return and refund policies, support contact details, and terms-of-service agreement collection. This is one of the areas where the old page was underspecified.

Stripe’s compliance warning is real

Stripe explicitly says you must not use custom text to create ambiguity with Stripe-generated text, your Stripe agreement, Stripe policies, or applicable law. If you customize reuse language or subscription terms, your legal team owns the correctness of that copy.

Custom text
Helpful context near the form
Use custom_text to add shipping notes, onboarding instructions, or a post-submit link. Stripe documents Markdown support for bold text and links, with a 1,200-character limit.
Submit button
Use submit_type for one-time payment wording
Set labels like donate or book so the CTA better matches the business action on Checkout.
Policies
Show return, refund, and legal information
Stripe exposes support contact info, return and refund details, terms-of-service links, and privacy policy links through Checkout settings.
Agreement collection
Require terms acceptance when needed
Checkout can collect a terms-of-service agreement before payment, which is especially useful for subscriptions or policy-sensitive flows.
cURL 
curl https://api.stripe.com/v1/checkout/sessions \
  -u "sk_test_...:" \
  -d "line_items[0][price]"="{{PRICE_ID}}" \
  -d "line_items[0][quantity]"=1 \
  -d mode=payment \
  --data-urlencode "custom_text[shipping_address][message]"="Please note that we can't guarantee 2-day delivery for PO boxes at this time." \
  --data-urlencode "custom_text[submit][message]"="We'll email you instructions on how to get started." \
  --data-urlencode "custom_text[after_submit][message]"="Learn more about **your purchase** on our [product page](https://example.com/products)." \
  --data-urlencode success_url="https://example.com/success"
Policy and text controls worth knowing
custom_text
Lets you add extra explanatory content near shipping fields, above submit, or after submit. Good for logistics notes, but not a place to rewrite Stripe’s compliance language.
submit_type
Changes the wording of the pay button for one-time purchases to align with actions like donate or book.
Support and policy settings
Configured in Checkout settings: support email, phone, website, return and refund terms, privacy policy, and terms of service links.
Payment method reuse text
Stripe lets you customize or hide some default reuse language, but not the payment-method-specific text. Stripe warns this is a compliance-sensitive area.

Filter card brands with brands_blocked

Stripe Checkout supports explicit card-brand filtering in both hosted and embedded page modes. The old page implied this was a vague visual tweak; it is actually a payment restriction, not just a logo preference.

Card-brand filtering propagates farther than the number field

Stripe documents that blocked brands are filtered in Apple Pay and Google Pay wallets, Link saved cards, customer saved payment methods, and co-badged networks where applicable.

Documented brand values
visa
Blocks Visa cards from Checkout.
mastercard
Blocks Mastercard cards from Checkout.
american_express
Blocks American Express cards from Checkout.
discover_global_network
Blocks the Discover Global Network family, including Discover, Diners, JCB, UnionPay, and Elo.
Node.js 
const session = await stripe.checkout.sessions.create({
  line_items: [
    {
      price: "price_12345",
      quantity: 1,
    },
  ],
  mode: "payment",
  success_url: "https://example.com/success",
  payment_method_options: {
    card: {
      restrictions: {
        brands_blocked: ["american_express"],
      },
    },
  },
});

Custom domains are for the Stripe-hosted page

Stripe’s custom domain docs are very specific: this feature is for Stripe-hosted Checkout pages, Payment Links, and the customer portal. It is not how you “brand” the embedded page, because the embedded page already lives on your own site.

Two DNS records, not one

The old page only showed a CNAME. Stripe’s actual setup requires both a CNAME pointing to hosted-checkout.stripecdn.com and a TXT record at _acme-challenge.<subdomain> for domain verification and TLS issuance.

DNS records 
Type:   CNAME
Name:   payments
Value:  hosted-checkout.stripecdn.com
TTL:    300

Type:   TXT
Name:   _acme-challenge.payments
Value:  [copy the exact verification string from Stripe Dashboard]
TTL:    300
Hosted flow

Valid use case

Point a subdomain like payments.example.com to Stripe so the hosted Checkout page feels branded and consistent.

Embedded page

Not the same feature

The embedded page already renders on your domain, so “custom domain for embedded Checkout” is a category mistake. What you customize there is the iframe’s branding and policy surface.

Add product images through Products or inline product_data

Stripe’s product image support is more straightforward than the old page made it seem. You can upload images on the Product in the Dashboard or pass them via the Products API, then reference a Price in Checkout. For one-off items, you can create the product inline inside the Session.

No invented image limits here

The previous page guessed at file limits and image counts. This rebuild avoids making up rules that the referenced Stripe page didn’t document and sticks to the actual product-image entry points Stripe describes.

Dashboard path
Edit the Product directly
Add a Description and upload an Image on the Product record, then reference its Price ID from the Checkout Session.
API path
Set images on the Product
When you create Products by API, Stripe documents the images parameter for reusable catalog items.
Inline path
Use line_items[].price_data.product_data
Ideal for dynamic or one-off purchases where you do not want a pre-saved catalog product.
Customer result
Checkout displays the image automatically
Stripe’s docs explicitly call this out once the Product or inline product data includes the image.
Inline product_data 
const session = await stripe.checkout.sessions.create({
  line_items: [
    {
      price_data: {
        currency: "usd",
        unit_amount: 1000,
        product_data: {
          name: "Premium T-Shirt",
          description: "Comfortable cotton t-shirt",
          images: ["https://example.com/t-shirt.png"],
        },
      },
      quantity: 1,
    },
  ],
  mode: "payment",
  success_url: "https://example.com/success",
});

Connect platforms inherit connected-account branding by default

This is an advanced but important detail from Stripe’s appearance docs. For destination charges with on_behalf_of and direct charges on platforms, Checkout uses the connected account’s branding by default. Platforms can manage branding for Express or Custom connected accounts through the Accounts API, and override it per Session with branding_settings.

Platform branding behavior
Connected account default
Checkout reads the connected account’s branding settings for the payment flow when the charge is effectively on that account’s behalf.
Accounts API
Platforms can configure branding for connected accounts that do not have full Dashboard access.
Per-session override
Set branding_settings when creating the Session if you need to override the connected account default for a specific Checkout flow.
