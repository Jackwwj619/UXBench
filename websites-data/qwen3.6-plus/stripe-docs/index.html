Why start with the Stripe-hosted page

The hosted UI is still the fastest way to ship Checkout. Stripe hosts the payment page, keeps the payment-method UX current, and can use a custom domain if you need the final checkout URL to look branded.

Hosted Checkout

Lowest integration effort

Customers leave your app for a Stripe-hosted payment page, then return to your site after payment. You create a Session, redirect to session.url, and listen for events like checkout.session.completed.

  • Best if you want the least custom frontend code.
  • Supports Stripe-managed UI updates and custom domains.
  • Great default when you do not need the payment form embedded in-page.
Embedded form

Same Sessions API, more in-page control

The embedded flow keeps customers on your site, but still uses Checkout Sessions and Stripe-hosted iframes for the secure payment UI. If you need that version, open the embedded guide in this rebuild.

  • Uses ui_mode: 'embedded_page' and return_url.
  • Mounted with stripe.createEmbeddedCheckoutPage().
  • Still limited customization compared with a fully custom Elements build.

2

Create a Checkout Session on your server

Create the Session on the backend, set your line items and URLs, then redirect the customer to the hosted Checkout page. For hosted Checkout, success_url and cancel_url are the important return points.

Hosted is the default Session mode

The Checkout Sessions API defaults ui_mode to hosted, so you normally omit it here. That keeps this guide aligned with Stripe’s current hosted quickstart instead of mixing in embedded-only parameters.

server.js 
const express = require("express");
const Stripe = require("stripe");

const app = express();
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);

app.post("/create-checkout-session", async (req, res) => {
  const session = await stripe.checkout.sessions.create({
    line_items: [
      {
        price: "price_12345",
        quantity: 1,
      },
    ],
    mode: "payment",
    success_url: "http://localhost:4242/success?session_id={CHECKOUT_SESSION_ID}",
    cancel_url: "http://localhost:4242/cancel",
  });

  res.redirect(303, session.url);
});

app.listen(4242, () => {
  console.log("Listening on http://localhost:4242");
});
server.py 
import os
import stripe
from flask import Flask, redirect

stripe.api_key = os.environ["STRIPE_SECRET_KEY"]
app = Flask(__name__)

@app.post("/create-checkout-session")
def create_checkout_session():
    session = stripe.checkout.Session.create(
        line_items=[
            {
                "price": "price_12345",
                "quantity": 1,
            }
        ],
        mode="payment",
        success_url="http://localhost:4242/success?session_id={CHECKOUT_SESSION_ID}",
        cancel_url="http://localhost:4242/cancel",
    )
    return redirect(session.url, code=303)

server.php 
<?php
require "vendor/autoload.php";

\Stripe\Stripe::setApiKey($_ENV["STRIPE_SECRET_KEY"]);

$session = \Stripe\Checkout\Session::create([
    "line_items" => [[
        "price" => "price_12345",
        "quantity" => 1,
    ]],
    "mode" => "payment",
    "success_url" => "http://localhost:4242/success?session_id={CHECKOUT_SESSION_ID}",
    "cancel_url" => "http://localhost:4242/cancel",
]);

header("HTTP/1.1 303 See Other");
header("Location: " . $session->url);
Key Session parameters for the hosted UI
line_items
The products or prices a customer is paying for. Stripe recommends using saved Price objects whenever practical.
mode
Use payment for one-time purchases, subscription for recurring billing, or setup to collect a reusable payment method.
success_url
Where Stripe sends the customer after a successful hosted Checkout flow. You can include {CHECKOUT_SESSION_ID} to fetch the final Session data on your success page.
cancel_url
Where the customer lands if they leave Checkout before the payment completes.

4

Show a success page, but fulfill from webhooks

The success page is useful for customer messaging, but Stripe’s docs are clear that it should not be your only fulfillment signal. Customers might never return to the page, close the tab, or lose connectivity after paying.

Do not ship from the success page alone

Use checkout.session.completed or related webhook events on the server to confirm payment and trigger fulfillment. Treat the success page as a display layer, not a source of truth.

success.html 
<h1>Thanks for your order</h1>
<p>We emailed your receipt and will update this order status shortly.</p>
Primary signal

checkout.session.completed

Use this event to start order fulfillment or mark the order as ready for the next step in your backend.

Related signal

checkout.session.async_payment_succeeded

Useful when the payment method finishes asynchronously and the initial checkout completion is not the final confirmation moment.

Test the hosted integration with current Checkout scenarios

These examples match Stripe’s current test-card guidance for Checkout. Use any future expiration date and any valid CVC unless the test case says otherwise.

Scenario Card number Expected result
Success 4242 4242 4242 4242 Payment succeeds and processes immediately.
3DS required 4000 0000 0000 3220 Triggers 3D Secure authentication before the payment completes.
Declined 4000 0000 0000 9995 Fails with an insufficient_funds decline.
Recommended local workflow

Use the Stripe CLI to forward webhooks locally while you test the hosted redirect flow: stripe listen --forward-to localhost:4242/webhook.
