Core concept

Stores.

A store is the unit of state in Runeforge. It owns a single piece of state, exposes actions to update it, and notifies subscribers when it changes. Stores are framework-agnostic — they have no knowledge of React, Solid, or any UI library.

Creating a store

Use forge() to create one. The shape of the object you pass is the API of the store.

import { forge } from "runeforge";

const session = forge({
  state: { user: null as User | null, expiresAt: 0 },
  actions: {
    login:  (s, user: User, ttl: number) => ({ user, expiresAt: Date.now() + ttl }),
    logout: ()                            => ({ user: null, expiresAt: 0 }),
  },
});

The returned store is a plain object with these methods, plus your actions as methods:

MemberSignatureDescription
get() => StateReturns the current state (a frozen snapshot).
set(next: Partial<State>) => voidImperative state update. Prefer actions in most cases.
subscribe(listener) => unsubscribeCalls listener on every committed state change.
select(selector) => SelectedViewReturns a derived view that's its own subscribable store.
reset() => voidReturns to the initial state. Useful in tests.
namestringAuto-derived debug name, or passed via the options bag.

Reading and subscribing

The simplest store is read with get() and observed with subscribe():

const current = session.get(); // { user: null, expiresAt: 0 }

const off = session.subscribe((next, prev) => {
  console.log("changed:", prev, "→", next);
});
// later
off();
State is immutable. Each commit replaces the previous state with a new frozen object. Don't try to mutate s.user.name = "x" — return a new object instead. Runeforge will warn in dev if it detects an in-place mutation.

Composing stores

Apps usually have several stores. They compose by importing each other and using derive():

import { derive } from "runeforge";
import { session } from "./session";
import { feed }    from "./feed";

export const homepage = derive(
  [session, feed],
  (s, f) => ({
    greeting: s.user ? `Welcome back, ${s.user.name}` : "Welcome",
    items:    s.user ? f.items : f.items.slice(0, 5),
  })
);

derive only recomputes when one of its inputs changes — and only emits a notification when its output changes (by structural equality). It's the right tool for "computed views" or "memoized selectors".

Slicing a store

For very large stores, store.select() returns a slice that behaves like its own store:

const currentUser = session.select((s) => s.user);

currentUser.subscribe((u) => render(u));
// fires only when `s.user` changes — not on `expiresAt` changes

Server-side rendering & serialization

Every store can be serialized with store.toJSON() and rehydrated with store.fromJSON(). The intended flow on the server is: create stores, prime them with fetched data, render once, ship the dehydrated state along with the HTML.

// server
session.login(user, 3600_000);
const html  = renderToString(<App />);
const state = { session: session.toJSON(), feed: feed.toJSON() };

// client
session.fromJSON(state.session);
feed.fromJSON(state.feed);
hydrate(<App />);

Testing stores

Stores are easy to unit-test because they have no framework. Just call actions and assert against store.get():

import { session } from "./session";

beforeEach(() => session.reset());

test("login sets the user and expiry", () => {
  session.login({ id: 1, name: "Milena" }, 60_000);
  const s = session.get();
  expect(s.user?.name).toBe("Milena");
  expect(s.expiresAt).toBeGreaterThan(Date.now());
});
